# Moyu Chat v0.0.1 design baseline

Status: v0.0.1 RC. The Android project compiles (debug + release with R8), the JVM unit-test suite (Robolectric SQLite + mock SSE servers for all three protocols) and emulator instrumented tests (bridge absent / bridge present) pass. Real-endpoint smoke exists behind `SMOKE_REAL=1` and has **not** been executed in this environment (no provider credentials available); it must not be reported as verified until actually run.

## Product goal

Moyu Chat is the supplemental, standalone Android chat application beside Moyu Remote and Moyu Server/UI. Its normal chat path must work with no PC, no Moyu Server, no EasyTier and no Remote database.

v0.0.1 focuses on the parts that actually define chat quality and maintainability:

1. a provider-neutral authoritative transcript;
2. prompt/context construction;
3. protocol encoding for common API families;
4. immutable local branching from either Chat or Remote snapshots;
5. explicit handoff back to Remote.

It deliberately does not implement tokenizer/inference/decoding, agent tools, MCP, RAG, provider catalogues or automatic Remote mutation.

## Design sources and adopted ideas

### OpenAI / Codex

Codex's published agent-loop design treats the prompt as a structured list of model-visible items and keeps requests replayable. The current Codex implementation separates durable rollout/session history from prompt-facing history and installs replacement history at compaction checkpoints. Static prompt prefixes are kept stable for prompt-cache reuse. The built-in compact prompt is a handoff/checkpoint summary focused on progress, decisions, constraints and next steps.

Moyu adopts the principles, not the coding-agent prompt itself:

- authoritative history and active model context are different things;
- provider continuation IDs are optional optimization state, never Moyu session identity;
- stable app instructions live outside imported conversation history;
- compaction/reduction must not delete the durable transcript;
- imported source summaries/checkpoints should replace old model-visible source history rather than being flattened beside it;
- recent turns should remain as lossless as practical.

### Anthropic / Claude

Anthropic Messages keeps `system` separate from `messages`; every active message/tool/image block counts toward the context window. Anthropic recommends server-side compaction for very long conversations and returns compaction blocks that are round-tripped in later stateless requests. Prompt caching benefits from keeping the system prefix stable and separately cacheable.

Moyu adopts:

- a stable product instruction prefix;
- a provider-neutral conversation body;
- provider compaction/cache as an optional transport optimization, not storage authority;
- complete local history remains available even when the active provider context is reduced.

## Source of truth

`ChatDatabase.timeline` is the complete local transcript. It is never rewritten merely because a provider's context window is full.

`CanonicalPrompt` is disposable derived state built for a single model request. It consists of:

- stable Moyu instructions;
- optional branch-boundary instructions;
- a bounded sequence of user/assistant messages;
- metadata describing truncation and estimated context usage.

This is the central invariant of v0.0.1.

## Provider protocols

Built-in protocol IDs:

- `openai-responses`
- `openai-chat-completions`
- `anthropic-messages`

Provider configuration selects a protocol. Sessions do not know wire formats.

v0.0.1 deliberately sends stateless/replayable context on every turn. It does not require `previous_response_id`, Anthropic server sessions, or any provider-native conversation identifier. This is slower on the wire but maximizes third-party endpoint compatibility and keeps Moyu state portable.

The OpenAI Responses route is the preferred GPT path. Chat Completions is kept as the broad compatibility path for services that implement the older OpenAI-compatible surface. Anthropic Messages supports Anthropic-compatible third-party endpoints.

## Prompt policy

The app prompt is intentionally small. It defines only durable product semantics:

- the assistant is operating inside Moyu Chat;
- only explicitly supplied current context/capabilities exist;
- imported Remote history is historical context, not an active PC runtime;
- source system/developer prompts, approvals and hidden reasoning are not inherited as current instructions;
- if old context has been omitted due to budget, do not claim it was seen.

Provider- or model-specific personality prompts are out of scope for v0.0.1.

## Context projection

Default model-visible items:

- local user messages: keep;
- local assistant visible answers: keep;
- imported user/assistant visible messages: keep;
- hidden thinking/reasoning: drop;
- usage/transport/error bookkeeping: drop;
- Remote approvals: drop;
- Remote tool calls/results: excluded in v0.0.1 unless later normalized by an explicit safe projector;
- source `system`/`developer` content: drop from imported snapshots.

The goal is continuation of the user's problem, not simulation of the original coding agent runtime.

## Context budget

Exact tokenization is intentionally not implemented in the APK. `ContextBudgetManager` uses a conservative UTF-8/code-point estimate and provider-configured context/output budgets.

Selection policy:

1. reserve space for product instructions and output;
2. preserve the newest conversational tail first;
3. keep chronological order in the final prompt;
4. mark the prompt as truncated when older content is omitted;
5. never mutate the stored transcript because of truncation.

Semantic model-generated compaction is deferred until it can be implemented without making a provider-specific summary the source of truth.

## Snapshot / branch

A branch is a normal Chat session with `originSnapshotId` and optional `parentSessionId`.

Creating a local branch:

1. freeze normalized user/assistant items through a selected local sequence;
2. persist them as an immutable Snapshot;
3. create a new Chat session referencing that Snapshot;
4. future sends build context from Snapshot + branch-local timeline.

Creating a Remote branch:

1. query the optional `RemoteDataBridge` for safe source summaries;
2. request one normalized bounded snapshot;
3. validate and copy the payload into Chat's own DB;
4. create the branch;
5. never dereference Remote data again for that branch.

## Remote bridge

Remote is an optional context source, not Chat's database backend.

Allowed semantic operations:

- status/capabilities;
- list normalized locally cached source sessions;
- export one normalized snapshot;
- accept an explicit handoff package.

Forbidden:

- arbitrary SQL/table access;
- reading node/network/provider credentials;
- mutating Remote cached sessions;
- sending to PC runtimes on Chat's behalf without an explicit Remote-side user action.

## Handoff

A handoff is explicit export, not synchronization. v0.0.1 stores a local draft derived from a branch and can submit it only when the Remote bridge is available. Failed submission remains a draft/failed record; it is never automatically replayed later.

## Release boundary

RC status of the local-agent completion checklist before a real v0.0.1 APK:

- compile Android project — done (debug + release/R8, AGP 8.2.2 / Gradle 8.5 / JDK 17);
- run Java/unit/static checks — done (static architecture checks, Robolectric + MockWebServer unit tests);
- verify WebView asset sync — done (gradle `syncMoyuChatUi` wired into preBuild);
- smoke both OpenAI protocol paths and Anthropic Messages with controlled endpoints — done via mock SSE conformance tests; **real-endpoint smoke NOT executed (no credentials), env-gated suite provided**;
- verify streaming cancellation and HTTP errors — done (unit tests: cancel/error/completed terminal mapping, single-terminal guarantee);
- verify offline startup with no Remote APK — done (Robolectric E2E + emulator instrumented test);
- verify local branch Snapshot immutability — done (unit tests);
- implement/verify the matching signature-protected bridge on Moyu Remote — implemented and verified on emulator (4/4 instrumented tests, handoff persisted to Remote-side inbox); production Remote release builds must pick up the bridge code;
- inspect APK/network security and ensure API keys never enter the WebView — done (envelope + SQLite full-table scans in tests; loopback-only cleartext via network security config).
